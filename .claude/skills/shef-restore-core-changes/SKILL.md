# Вернуть правки ядра после обновления

Операция: после обновления Битрикса найти правки, которые обновление
перезаписало, и вернуть их так, чтобы учёт снова сходился. Учёт ведёт модуль
[shef.haschangefiles](https://github.com/bx-shef/haschangefiles): рядом с
каждым исправленным файлом лежит зеркало `has-change_<имя>` — копия файла с
правкой.

## 1. Что разошлось

```bash
cd <корень сайта>
php bitrix/modules/shef.haschangefiles/cli/check-core-changes.php --diff > /tmp/core-changes.txt
echo $?
```

Модуль в `/local/modules` — путь `local/modules/shef.haschangefiles/cli/…`.
Код `0` — всё на месте, делать нечего. Код `2` — не найден корень сайта (в
каталоге нет `/bitrix`) или каталог `BASE_DIR`: задайте
`DOCUMENT_ROOT=<корень>`. Код `1` — разбирать строки:

| строка | `Status` | что делать |
|---|---|---|
| `OK` | `\Shef\Haschangefiles\Main\Status::Ok` | ничего |
| `DRIFT` | `\Shef\Haschangefiles\Main\Status::Drift` | файл разошёлся с зеркалом — вернуть правку, шаг 2 |
| `NO-MARKERS` | `\Shef\Haschangefiles\Main\Status::NoMarkers` | файл и зеркало совпадают, но пометки нет — добавить `// change ////` в оба, шаг 3 |
| `NO-ORIGINAL` | `\Shef\Haschangefiles\Main\Status::NoOriginal` | ядро удалило или переименовало файл — шаг 4 |

`--diff` печатает под каждым `DRIFT` вывод `diff -u <зеркало> <файл>`: строки
с `-` — то, что было с правкой, с `+` — новый код ядра.

Без консоли — **Настройки → Правки ядра → Учёт правок** в административной
части: «Восстановить», «Нет пометки», «Нет файла».

## 2. DRIFT — вернуть правку

Зеркало **не копировать поверх файла**. В зеркале старая версия ядра: вернуть
её целиком — значит откатить обновление этого файла, а с ним исправления
безопасности и совместимость с остальным новым ядром.

Для каждого файла:

1. Найти в зеркале блоки `// change ////` … `// change stop ////`.
2. Найти то же место в новом файле. Закомментированный внутри блока прежний
   код — ориентир: если ядро это место не меняло, он совпадает с текущим
   кодом нового файла.
3. Перенести правку в новый файл, в том же оформлении блоком.
4. **Пересохранить зеркало** из нового файла: `cp <файл> has-change_<файл>`.
   Зеркало обязано быть копией файла с правкой — иначе строка останется
   `DRIFT`.

Место правки в новом ядре переписано, и правка не ложится как есть — не
угадывайте: опишите человеку, что изменилось в ядре и чем правка теперь
мешает или помогает. Возможно, ядро само исправило то, ради чего правили, и
правка больше не нужна — тогда удаляется и зеркало, но только с согласия
человека.

## 3. NO-MARKERS

Правка на месте, но не помечена. Найти изменённое место (сравнить с чистым
файлом ядра той же версии или спросить человека), обрамить `// change ////`
… `// change stop ////`, скопировать файл в зеркало заново.

## 4. NO-ORIGINAL

Зеркало есть, файла нет. Ядро удалило файл или перенесло его код. Искать,
куда ушёл код (`grep` по имени класса или функции в `/bitrix`), и решать
вместе с человеком: переносить правку в новое место (новый файл — новое
зеркало рядом с ним) или правка больше не нужна. Старое зеркало удалить
после решения — иначе строка будет висеть всегда.

## 5. Довести до нуля

Повторять проверку, пока код возврата не станет `0`. Затем — открыть на
портале страницы, которые правки затрагивают: проверка сверяет файлы, а не
то, что сайт работает.

## Чего не делать

* не копировать зеркало поверх обновлённого файла (см. шаг 2);
* не «чинить» строку, пересохранив зеркало из файла без правки: строка станет
  `NO-MARKERS`, а если в файле есть другие помеченные блоки — `OK`, и правка
  пропадёт молча и навсегда;
* не выкладывать перенесённые правки на портал клиента самому: вы готовите
  файлы и зеркала (или диф), выкладывает человек — это правка ядра чужого
  портала;
* не удалять зеркала без решения человека: это единственная память о том,
  что файл правили.
