# Правка ядра по правилам

Операция: изменить файл Битрикса в `/bitrix` (или ядерный файл в корне
сайта) так, чтобы после обновления платформы было видно, что правка была и
что её перезаписало. Учёт ведёт модуль
[shef.haschangefiles](https://github.com/bx-shef/haschangefiles): он ищет
зеркала `has-change_<имя>` и сравнивает их с файлами рядом.

## 0. Сначала — можно ли без правки ядра

Правка ядра — долг: каждое обновление её стирает. Прежде чем трогать
`/bitrix`, проверьте по порядку:

| что правите | чем заменить |
|---|---|
| шаблон компонента `/bitrix/components/bitrix/<имя>/templates/…` | скопировать шаблон в `/local/templates/<шаблон сайта>/components/bitrix/<имя>/` или `/local/templates/.default/components/bitrix/<имя>/` и править там |
| поведение класса модуля при сохранении, удалении, выводе | обработчик события модуля (`EventManager`) в своём модуле |
| компонент целиком | свой компонент в `/local/components` или в своём модуле |
| js-расширение | своё расширение, подключённое после штатного |

Нашлась замена — делайте её, а не правку ядра, и дальше этот навык не нужен.
Не нашлась — скажите это человеку одной строкой (что правите и почему без
ядра нельзя) и идите дальше.

## 1. Пометить правку

Изменённое обрамляется блоком `// change ////` … `// change stop ////`, прежний
код остаётся закомментированным внутри блока — по нему видно, что было:

```php
foreach($list as $item)
{
	// change ////
	// $item['NAME'] = $item['CODE']; ////
	$item['NAME'] = sprintf('[%s] %s', $item['ID'], $item['CODE']);
	// change stop ////
}
```

В JS — те же комментарии `// change ////`. В шаблоне с HTML — внутри
`<?php // change //// ?>` … `<?php // change stop //// ?>`.

Без маркера модуль покажет правку как «Нет пометки»
(`\Shef\Haschangefiles\Main\Status::NoMarkers`): файл и копия совпадают, но
найти правку в файле глазами нельзя. Маркер ищется подстрокой `// change`
(засчитываются и `//change`, `//cahnge`, `// cahnge`) — не выдумывайте свой.

Одна правка — один блок. Несколько мест в файле — несколько блоков.

## 2. Сохранить зеркало

Файл **с правкой** копируется рядом под именем `has-change_<имя>`:

```bash
cp bitrix/modules/crm/lib/order.php bitrix/modules/crm/lib/has-change_order.php
```

Зеркало — точная копия файла после правки, байт в байт. Модуль сравнивает
**содержимое** (`\Shef\Haschangefiles\Main\Utils::isSameContent()`): поправили
файл ещё раз и не пересохранили зеркало — отчёт покажет «Восстановить», хотя
обновления не было.

Зеркало живёт там же, где файл, и едет на сервер вместе с ним. В репозитории
проекта его коммитят рядом с правкой.

Зеркало `.php` в каталоге, который отдаёт веб-сервер
(`/bitrix/components/…/ajax.php`, `/bitrix/tools/`, публичная часть), —
исполняемая по URL копия кода. На сервере должно стоять правило, закрывающее
`has-change_*` (nginx: `location ~ /has-change_ { deny all; }`, подробности —
[security.md](https://github.com/bx-shef/haschangefiles/blob/main/docs/security.md)).
Не знаете, стоит ли, — скажите об этом человеку.

## 3. Проверить

На сервере или на копии сайта:

```bash
php bitrix/modules/shef.haschangefiles/cli/check-core-changes.php
```

Модуль стоит в `/local/modules` — путь `local/modules/shef.haschangefiles/cli/…`.
Корень сайта другой — `DOCUMENT_ROOT=/путь/к/сайту` перед командой.

Ваша правка обязана быть в выводе строкой `OK`, код возврата — `0` (если
других расхождений на сайте нет). В административной части то же видно в
**Настройки → Правки ядра → Учёт правок**.

Модуля на портале нет — зеркало всё равно кладите: это договорённость, и
модуль, поставленный позже, найдёт все правки сразу. Проверить можно
глазами: `cmp файл has-change_файл` молчит, в файле есть `// change`.

## Чего не делать

* не выкладывать правку на портал клиента самому: вы готовите правку и
  зеркало (диф, файлы), выкладывает человек — это правка ядра чужого
  портала, необратимое для агента действие;
* не править по этому навыку `/local`, свои модули и
  `/bitrix/php_interface` (`init.php`, `dbconn.php`) — это код проекта,
  обновление его не перезаписывает и зеркало ему не нужно. Отчёт и
  консольная проверка `/local` не обходят; `/bitrix/php_interface` обходят
  (он внутри `/bitrix`), но зеркало там — лишнее;
* не класть зеркало в другой каталог и не называть его иначе: модуль ищет
  ровно `has-change_<имя>` рядом с файлом;
* не делать зеркало **до** правки — это копия исходника ядра, и отчёт сразу
  покажет «Восстановить»;
* не удалять прежний код, а комментировать его внутри блока: после
  обновления по нему сверяют, изменило ли ядро то место, которое правили.
