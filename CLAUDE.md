# Памятка агенту: shef.haschangefiles

Модуль Битрикс24 «коробки» и БУС для учёта правок ядра: правка помечается
`// change ////` в коде, рядом лежит зеркало `has-change_<имя>`, а модуль
после обновления платформы показывает, какие правки перезаписаны. Опирается на
`shef.options` и сделан по его канону — сборка, тесты, раскладка, решения,
ловушки. Если здесь чего-то не хватает, смотрите
[CLAUDE.md shef.options](https://github.com/bx-shef/options/blob/main/CLAUDE.md):
всё, что там сказано про устройство модуля линейки, верно и здесь.

Проверка перед сдачей — всегда `./build.sh --check`, ровно это же гоняет CI.

Тесты лежат в `tests/`, гоняются как обычные скрипты. Обвязка
`tests/assert.php` общая с shef.options: сравнение строгое, warning и notice —
провал. Ядро подменяется заглушками из `tests/stub/bitrix.php`, API страницы
настроек shef.options — `tests/stub/options.php`, классы модуля подключаются
**настоящие** автозагрузкой `tests/stub/autoload.php` — по тому же соглашению,
что на портале.

| тест | что держит |
|---|---|
| `autoload_test.php` | класс лежит там, где его ищет ядро; один FQCN — один файл |
| `settings_test.php` | `.settings.php`: обработчики существуют, `installDir` пуст, shef.uiclear не зовётся нигде в коде поставки |
| `scanner_test.php` | состояние правки (содержимое, а не размер), путь оригинала, обход без ссылок и нечитаемых каталогов; классы — без ядра |
| `report_test.php` | строка отчёта экранирована, ссылка в PhpStorm закодирована, подписи есть |
| `cli_test.php` | консольная проверка: коды 0/1/2, `BASE_DIR`, `--diff`, корень сайта сам |
| `events_test.php` | страница обновлений: где и кому кнопка, один раз за запрос, заглушка 1.x, скрипт — верный JS |
| `adminmenu_test.php` | меню «Правки ядра»: только администратору, страница отчёта кладётся сама |
| `adminpage_test.php` | заглушка страницы отчёта: путь — где стоит модуль, удаляется только своя |
| `optionsconf_test.php` | `options_conf.php` собирается против API shef.options 3.x |
| `include_test.php` | подключение модуля поднимает shef.options и больше ничего |
| `uninstall_test.php` | установка ничего не копирует и убирает каталоги 1.x; удаление уносит настройки, обработчики (включая два из 1.x) и свою заглушку, чужое не трогает |
| `composer_test.php` | тип пакета, `installer-name`, потолок `composer/installers` |
| `docs_test.php` | ссылки в `*.md` живые, классы и методы из документации существуют |
| `examples_test.php` | каждый пример из `examples/` запускается и сходится с обещанным |
| `skills_test.php` | навыки оформлены, копия сходится с `MANIFEST`, локальные навыки — с `LOCAL.MANIFEST` |
| `evals_test.php` | evals навыков разбираются |

`events_test.php` зовёт `node --check` на скрипт подтверждения: нет `node` —
тест краснеет, а не пропускает проверку.

**Навыки — двух видов.** Навыки линейки (`shef-options-*`, `shef-new-*` и
прочие из `MANIFEST`) — **копия**: их раскладывает `sync.sh --to` из
[bx-shef/options](https://github.com/bx-shef/options), там же их и правят.
Задача `Skills` в CI сверяет копию с источником и краснеет, когда источник
ушёл вперёд — это сигнал разложить заново, а не чинить копию.

Навыки про работу с правками ядра — **локальные**, их источник здесь:
`shef-core-change` (внести правку в ядро: сначала поискать замену без ядра,
потом пометка `// change ////` и зеркало) и `shef-restore-core-changes`
(вернуть правки после обновления Битрикса по консольной проверке). Они
перечислены в `.claude/skills/LOCAL.MANIFEST`: после правки —
`.claude/skills/sync.sh --local`, иначе `--check` краснеет; `sync.sh --to`
их не трогает. Оформление — по правилам `.claude/skills/README.md` (evals
обязательны), классы `\Shef\Haschangefiles\...` из навыков проверяет
`tests/docs_test.php`, наличие — `tests/skills_test.php`.

Навыки пересказывают договорённости модуля дословно: маркер, имя зеркала,
состояния, коды возврата и путь консольной проверки. Поменяли что-то из
этого — правьте и навык.

**Примеры в `examples/` запускаются, а не читаются.** Как в shef.options:
`php examples/x.php` — на заглушках, `DOCUMENT_ROOT=/var/www/portal php
examples/x.php` — на живом портале. Шапка — ЦЕЛЬ, ГДЕ ПРИМЕНЯТЬ, ЧТО ДОЛЖНО
ПОЛУЧИТЬСЯ, ЗАПУСК. Файлы сайта примеры не трогают ни в одном режиме: «сайт»
с правками — во временном каталоге (`sandbox()` в `_bootstrap.php`).

## Опорные точки

**Состояние правки — одно правило на всех.** `Main\Utils::getStatus()`: нет
оригинала — `NO-ORIGINAL`; содержимое разошлось с зеркалом — `DRIFT`; совпадает,
но маркера нет — `NO-MARKERS`; иначе `OK`. Его зовут `Main\ChangeFile` →
страница отчёта и консольная проверка. Второй копии эвристики нигде нет и не
должно быть: в 1.0.x она жила в компоненте, в 1.1.0 её вынесли — ради этого.

**Четыре класса самодостаточны:** `Status`, `Utils`, `ChangeFile`, `Scanner`
не зовут ни ядро, ни `Loc`. Консольная проверка подключает их явным
`require_once` и ядро не поднимает — поэтому работает на копии сайта в CI.
Добавите в них вызов ядра — `scanner_test.php` и `cli_test.php` упадут fatal.
`Report` уже зовёт `Loc` и в консоли не используется.

**Отчёт — страница административной части без компонента.**
`admin/list.php` открывается заглушкой `/bitrix/admin/shef_haschangefiles_list.php`,
которую **пишет** `Main\AdminPage` (путь — туда, где модуль стоит). Пишут
установщик (`InstallFiles()`) и меню на портале, обновлённом заменой файлов
(`AdminMenu::ensureListPage()`). Разделы, колонки и строки собирает
`Main\Report`, грид — штатный `main.ui.grid`. Права — `$USER->IsAdmin()` и в
меню, и на странице.

**Меню** — `admin/menu.php`, раздел в «Настройках». Ядро подключает файл само
для каждого установленного модуля; регистрировать и копировать не нужно.

**Страница обновлений** — `main:OnAdminContextMenuShow` →
`Integration\Main\Events::onAdminContextMenuShow()`: кнопка «Правки ядра» и
диалог перед «Установить обновления». Только `update_system.php`, только GET,
только администратору, один раз за запрос. Тексты в скрипт — через
`json_encode`.

**Установщик** — `install/index.php`, каноническая копия из shef.problems
(`getModuleDir()`, `savedata`, проверка UTF-8 и версий) плюс:
`NEED_MODULES_BY_VERSION` = `shef.options` 3.0.0, `getLegacyEventsList()` (два
обработчика 1.x на класс `Integration\Shef\UiClear\Events`),
`getLegacyDirList()` (`/bitrix/images`, `/local/admin`, `/local/components` —
всё `shef.haschangefiles`; убирается и при установке, и при удалении), заглушка
страницы отчёта через `AdminPage`. `installDir` пуст.

**Namespace — `Shef\Haschangefiles`**, именно с одной заглавной: так он
записан в регистрациях обработчиков на порталах с 1.x, а `UnInstallEvents()`
снимает их по строке.

## Решения владельца

Это решения, а не баги. Не переигрывать без просьбы.

**База — рабочая копия 1.0.6, функциональность — из 1.1.0.**
Владелец прислал три архива; разбор — ниже, в «Рабочие копии».

**shef.uiclear не используем — штатные возможности Битрикс24.** Пункт на
верхней панели — раздел меню административной части; bootstrap и карточки
шаблона — не нужны, страница административная; цвет «опасно» —
литералом `Events::DANGER_COLOR` вместо `\Shef\UiClear\Css\Color::danger`.
Класс `Integration\Shef\UiClear\Events` — заглушка для порталов, обновлённых
с 1.x, у которых регистрация обработчиков осталась; удалять со следующей
мажорной версией.

**Composer — `bxshef/haschangefiles`, тип `bitrix-module`**, `installer-name =
shef.haschangefiles`, лицензия MIT, потолок `composer/installers`. Всё — ровно
как в shef.options и по тем же причинам (см. его CLAUDE.md, «bitrix-d7-module
развернул бы модуль не туда»). В 1.x стояло `shef/haschangefiles` +
`bitrix-d7-module` + `proprietary`, требования `shef/options ^2.2` и
`shef/uiclear ^1.1`.

**Модуль поставляется только в UTF-8**, **настройки уходят вместе с модулем**
(`savedata = Y` оставляет) — как в shef.options.

**Компонента `shef.haschangefiles:list` больше нет.** Он был нужен ровно одной
странице, требовал раскладки в `/local/components`, а на портале, обновлённом
заменой файлов, компонент 1.x из `/local` перекрыл бы новый и упал бы на
`Utils::needFix()`. Страница административной части рисует грид сама из
`lib/`, и обновлению заменой файлов раскладывать нечего. Не возвращать без
просьбы; нужен отчёт в другом месте — `Report::getRow()` отдаёт готовые
строки `main.ui.grid`.

**Сравнивается содержимое, а не размер.** В 1.x (и в 1.1.0, где эвристику
«сохранили 1:1») правка считалась на месте, если совпадал размер. Зеркало по
договорённости — копия файла с правкой, значит, «на месте» — это «совпадает».

**Документация живёт в репозитории.** В поставке — только README, ссылки из
него на GitHub. Скриншоты 1.x (`install/images`) не перенесены: они
показывали страницу 1.x на bootstrap из shef.uiclear, которой больше нет.

## Рабочие копии

Копии названы по версиям, а не по именам архивов: имена архивов — сокращения
заказчиков, а репозиторий публичный.

| копия | что это |
|---|---|
| 1.0.6 (2023-09-22) | **база** по слову владельца. Четыре файла пересохранены в CP1251 — отличаются от 1.0.6-utf только комментариями |
| 1.0.6-utf | та же 1.0.6 целиком в UTF-8; архив самый старый (2024-12) |
| 1.1.0 (2026-08-25) | 1.0.6 плюс `Main\Utils` (эвристика вынесена из компонента) и `cli/check-core-changes.php`. Пришла тремя архивами: модуль, компонент, страница — компонент и страница совпадают с теми, что внутри модуля |

История в репозитории: импорт 1.0.6 (в UTF-8, то есть ровно 1.0.6-utf),
потом дельта 1.1.0, потом приведение к канону — каждое отдельным коммитом.

**Взято из 1.1.0:** вынос эвристики в `Utils`, `isMirrorName()`,
`originalPath()`, `countChangeMarkers()`, консольная проверка. `needFix()`
заменён `getStatus()` (содержимое вместо размера).

**Не взято:** ссылки на `docs/infra/bitrix-update.md` и
`docs/infra/core-changes.md` и упоминание юнит-тестов в CHANGELOG 1.1.0 —
это файлы проекта заказчика, в архиве их нет.

## Ловушки, за которые заплачено

**Размер — не содержимое.** Обновление, заменившее в файле символ на символ,
оставляет размер прежним. В 1.x такой файл был «правкой на месте».
`scanner_test.php` держит именно этот случай.

**Замена префикса по всему пути.** Компонент 1.x считал путь оригинала как
`str_replace('has-change_', '', $path)`: каталог с тем же сочетанием букв
ломал путь. `Utils::originalPath()` снимает префикс только с имени файла.

**Рекурсивный обход и символические ссылки.** `scandir()` + `is_dir()` в 1.x
шли по ссылкам: ссылка наверх (общий `/bitrix` нескольких сайтов, ссылка на
корень) — бесконечная рекурсия; нечитаемый каталог — `scandir()` отдаёт
`false`, `count(false)` — `TypeError`. `Scanner::find()` по ссылкам на
каталоги не ходит и нечитаемые пропускает (`CATCH_GET_CHILD`).

**Регистрация обработчика переживает замену файлов.** В 1.x оба
обработчика были зарегистрированы на `Integration\Shef\UiClear\Events`. Класс
оставлен: на shef.uiclear отвечает «нечего добавить», страницу обновлений
передаёт новому обработчику. Если на портале окажутся обе регистрации —
старая и новая, — кнопка не задвоится: обработчик отрабатывает один раз за
запрос.

**Замена файлов не запускает установщик.** Страницу отчёта в `/bitrix/admin`
на обновлённом портале кладёт меню (`ensureListPage()`), а каталоги 1.x в
`/local` остаются до `InstallFiles()` — порядок в
[docs/portal-check.md](docs/portal-check.md), шаг B.

**В `/bitrix/admin` удалять только своё** — как в shef.problems:
`AdminPage::isOwn()` сверяет содержимое, а не имя.

**Вывод отчёта — это HTML.** Имя файла и путь — с диска, а публичную часть
сайта наполняют не только разработчики. Экранирует `Report::getRow()`.

**Тексты в скрипт — через `json_encode`, а не в кавычки.** В 1.x
подтверждение собиралось `"<?=$confirm->message?>"`: кавычка в переводе —
синтаксическая ошибка, и кнопка «Установить обновления» не работала вовсе.

**Два грида — два `GRID_ID`.** В 1.x оба раздела отчёта брали один
`GRID_ID` по умолчанию, и настройки грида одного раздела доставались другому.

**Проверяй артефакт, а не свой диф** — как в shef.options.

## Известные шероховатости

Не трогать заодно — отдельной задачей, с проверкой на портале.

* Отчёт обходит `/bitrix` целиком на каждый показ, кеша нет. На портале с
  большим ядром это секунды. Кеш — отдельной задачей: инвалидировать его
  пришлось бы по времени изменения файлов, а это тот же обход.
* Маркер правки ищется подстрокой: `// changed` в чужом комментарии тоже
  засчитывается. Так было всегда; `scanner_test.php` это фиксирует, чтобы не
  поменялось молча.
* `--diff` в консольной проверке зовёт системный `diff`; нет его — разница
  просто не печатается.
* Подтверждение ставится на кнопки `install_updates_button` и
  `install_updates_sel_button` и функции `InstallUpdates()` /
  `InstallUpdatesSel()` страницы обновлений ядра. Переименует их ядро —
  диалог молча перестанет появляться (скрипт проверяет, что функции есть, и
  без них кнопки не трогает). Страница обновлений партнёрских модулей не
  охвачена.
* `tests/stub/options.php` повторяет API страницы настроек shef.options 3.x.
  Поменяется API — заглушку менять вместе с ним.

## Приёмочный чек-лист

Процедура — [docs/portal-check.md](docs/portal-check.md): шаги с ожидаемым
результатом и бланк. Проходить **перед сдачей** и **на отдельном стенде**.

Главный сценарий для 2.0.0 — обновление со стенда с 1.x: страница настроек
открывается с `shef.options` 3.x, меню «Правки ядра» на месте и страница
отчёта появилась сама, кнопка на странице обновлений — одна, после
`InstallFiles()` страницы 1.x в `/local` нет.
