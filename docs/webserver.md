# Закрыть зеркала от веб-сервера

Зеркало правки `has-change_<имя>` лежит рядом с исправленным файлом. Если
каталог отдаёт веб-сервер (`/bitrix/components/…/ajax.php`, `/bitrix/tools/`,
публичная часть), зеркало `.php` **исполняется по URL**. После обновления
Битрикса это прежняя версия файла — в том числе та, в которой обновление
закрыло уязвимость, — и лежит она так, пока правку не вернут. Почему так
вышло и почему имя зеркала не меняем — [security.md](security.md).

Решение владельца: закрывать правилом веб-сервера на каждом портале, где
стоит модуль. Модуль сам конфигурацию веб-сервера не трогает — это делает
администратор сервера по этой инструкции.

## Что должно получиться

Любой адрес, в пути которого есть `has-change_`, отвечает **403** — и `.php`,
и остальные файлы. Проверка одна на оба сервера, её и считайте результатом:
конфигурации у порталов разные, и «добавил строку» ещё не значит «закрыто».

```bash
cd <корень сайта>
echo '<?php echo "open";' > bitrix/tools/has-change_probe.php   # безвредный PHP: откроется — напечатает «open»
echo 'open' > bitrix/tools/has-change_probe.txt
curl -s -o /dev/null -w '%{http_code}\n' https://<портал>/bitrix/tools/has-change_probe.php   # 403
curl -s -o /dev/null -w '%{http_code}\n' https://<портал>/bitrix/tools/has-change_probe.txt   # 403
rm bitrix/tools/has-change_probe.php bitrix/tools/has-change_probe.txt
```

`200` на первой строке — правило не сработало, зеркала открыты.

## nginx

Правило:

```nginx
location ~ /has-change_ {
	deny all;
}
```

1. Найти блок `server { … }` сайта:

   ```bash
   nginx -T 2>/dev/null | grep -n 'server_name\|# configuration file'
   ```

   Строка `# configuration file <путь>` над нужным `server_name` — файл, в
   котором блок лежит. На BitrixVM и в «Битрикс: веб-окружении» это свои
   файлы окружения; какой именно у портала — смотрите здесь, а не по памяти.
2. Вставить правило **внутрь** `server { … }`, **выше** всех
   `location ~ …` (особенно `location ~ \.php$`). Регулярные `location`
   nginx проверяет по порядку, и побеждает первое совпадение: правило ниже
   обработчика PHP не сработает никогда.
3. Проверить конфигурацию и перечитать её:

   ```bash
   nginx -t && systemctl reload nginx
   ```

4. Проверка из раздела «Что должно получиться».

**Если всё равно 200.** Значит, адрес забирает `location ^~ /…` (префиксный
с `^~`): после него регулярные `location` не проверяются вовсе. Найдите его в
выводе `nginx -T` и положите то же правило **внутрь** этого `location`.
Повторите проверку.

Если за nginx стоит Apache (как на BitrixVM), закройте и его — правило ниже:
запрос в обход nginx на порт Apache иначе отдаст файл.

## Apache

В `.htaccess` в корне сайта (или в `<VirtualHost>` сайта):

```apache
<FilesMatch "^has-change_">
	Require all denied
</FilesMatch>
```

Это синтаксис Apache 2.4. На 2.2 вместо `Require all denied`:

```apache
<FilesMatch "^has-change_">
	Order allow,deny
	Deny from all
</FilesMatch>
```

`.htaccess` действует, только если для корня сайта разрешён
`AllowOverride` (у Битрикса он обычно разрешён — на `.htaccess` держатся
его ЧПУ). Проверка — та же, `curl` из раздела «Что должно получиться»;
Apache за nginx проверяйте запросом прямо на его порт.
